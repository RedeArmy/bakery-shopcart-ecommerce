## Done since the last update

- **Pool, access log and warm-up hardened** (9 November). The connection pool shares the connection in progress, so a second caller no longer receives a pool that is still connecting. The backend writes one `request` line per call with the route template, the status, the duration, the request id and the user, which makes the slow calls visible. The database warm-up runs when the connection is established and again every minute, so a restart of SQL Server does not hand the cold start to the first customer. Technical debt items 4, 5 and part of 6 of the review of 9 November.
- **The end-to-end suite is stable and runs in the CI** (9 November). The waits were 7 s and a call of the purchase flow took up to 6 s with the database cold, so the scenario failed for slowness; they are now 15 s, with a global set-up that waits for the application and warms the public reads, one retry in the CI and a `e2e` job that starts the stack and keeps the traces of a failure. The job is not a required check. Technical debt item 1 of the review of 9 November.
- **The staff land on their dashboard and do not see the shop** (9 November). An operator or an administrator who signs in goes to `/admin`, not to the catalogue; the home page, the catalogue, the cart and the checkout send them there, and they see no catalogue, no «my orders», no cart, no announcement bar about made-to-order cakes and no shop column in the footer, because they do not buy. The dashboard now greets by the first name («Hola Eder»). The customer and the visitor are unchanged.
- **Dashboards for the administrator and the operator** (9 November). `/admin` is the first entry of the staff menu and each role sees its own view. The administrator has the reports of RF-08: a period filter (7, 30 or 90 days, or two dates, grouped by day, week or month), the headline figures with what is pending now, the sales as bars of amount or orders with a table of the same data, sales by category, the ten best sellers and the orders of the period; every section has its own loading, empty and error state and a period that is reversed is explained without asking the server. The operator has the work to attend: orders to prepare, in preparation and dispatched, deposits under review and cash payments pending, each leading to its screen, and the lists of orders to prepare and to deliver. The order list now filters by date (`from` and `to`), which RF-08 asks for.
- **The operator manages the inventory** (9 November). RF-01 says that the operator manages orders and inventory, and until now the operator could only read the ledger. The stock entries and adjustments (`POST /admin/inventory/entries`, `/adjustments`) are now open to an active operator or administrator, in the routes and in the two procedures (`SP_Inventory_RegisterEntry` and `SP_Inventory_AdjustStock` 1.1.0, through the new `FU_Users_ActiveStaff`); the customer is still refused. Two tSQLt tests were added and two renamed.
- **The first checkout no longer waits for the time zone** (9 November). The first `AT TIME ZONE` of a SQL Server instance takes about 5 s, so the first payment step after each start took 7 to 9 s and the e2e purchase scenario failed on it. The backend now calls `SP_System_WarmUp` once at start-up and the first call takes 0.18 s. Not covered: a database restart while the backend keeps running brings the delay back for the first request, and the pool lets a second caller use it while it is still connecting (found while doing this, left alone).

## Spike results

- **tSQLt works on the Linux SQL Server image and on Docker Desktop (WSL2)**, so the first risk of the register is closed and plan B is not needed. It was verified with tSQLt 1.0.8083.3529 on SQL Server 2022 CU27, starting from `clr strict security` enabled. A failing test makes `sqlcmd -b` exit with code 1 and the results export as JUnit XML. The lessons for writing the tests (identity values are not rolled back, test order is not fixed) are in [the tSQLt testing document](../quality/sql-testing-tsqlt.md#spike-result-29-october-2026).

- **The demo accounts are created.** `npm run up` generates `SEED_ADMIN_PASSWORD`, `SEED_OPERATOR_PASSWORD` and `SEED_CUSTOMER_PASSWORD` in the local `.env` (also in an older one, without touching its values), and `db-migrate` hashes them with argon2id and creates `admin@`, `operator@`, `customer1@` and `customer2@shopcart.test` through `SP_Users_Provision`, which the application login cannot execute. The step is idempotent and off unless `SEED_DEMO_DATA=true`; `npm run seed` runs it alone. No password and no hash is in the repository. The demo catalogue, coupons, bank account and performance data are still to be written.
- **The runner no longer races the first start of SQL Server.** Its start-up gate used to treat any failed query as "ready" (a deadlock or a cut connection during the collation change let `CREATE DATABASE` through, which shuts the server down with error 3434). It now fails closed, confirms the settled state twice and, if the server still goes down, stops with `SERVER_SHUT_DOWN` and the fix. Cold starts were sampled every 300 ms to confirm the sequence it relies on.
- **The architecture diagrams match the system.** No card gateway, one API process with its jobs, the real module dependencies and the order lifecycle with several partial returns.
- **The delivery can be verified in minutes.** A Postman collection (38 requests, 66 assertions, in English and Spanish, run against the real stack and repeatable) proves authentication first and then the roles, the stock limit of the cart, the coupons, the 15 minute reservation, idempotency, ownership of data, the order lifecycle and the audit log. The acceptance criteria map links each of the 21 criteria of the brief to its tests, and the README (both languages) is up to date: status per requirement, how controllers and routes are organised, the open decisions in one table, the payment states and how to verify. Still missing before Phase 2: the demo catalogue, coupons and bank account seeds.
- **The database was reviewed and hardened.** Measured with 50,000 orders: the order list went from up to 483,437 reads and 252 ms to 767 reads and about 20 ms, the abandoned carts from 162,724 reads to 529, the audit log without filters from 3.3 seconds to 38 ms, and the stock ledger of a busy variant from 713 to 29 ms. Causes: `COUNT(*) OVER ()` spooling to `tempdb`, one cached plan for customers and staff, and a non-sargable filter. The database now runs with read committed snapshot isolation, a daily batched purge keeps the tables that only grow bounded, and `npm run sql:bench` guards the figures. Details and what was tried and rejected: [performance](../operations/performance.md).
- **The cart refuses a quantity above the stock** (RF-04 acceptance criterion). `SP_Cart_SetItemQuantity` answers `409 INSUFFICIENT_STOCK` when the quantity exceeds what is available (not reserved by others, counting the cart's own reservation), before creating anything; the checkout reservation stays the final guarantee. The guest-cart merge at sign-in respects the same limit by clamping (shared function `FU_Cart_AvailableStock`). Thirteen new tSQLt tests and one HTTP flow.
- **The dashboard exists** (RF-08). Five procedures over two views and three functions: a summary, the sales by day, week or month with the empty periods as zeros, the sales by category, the best sellers and the abandoned carts. Sales follow ADR-0009 (paid, not cancelled, by payment date in Guatemala time, net of returns) and the average ticket uses half-even rounding. Five administrator endpoints under `/admin/dashboard`, 23 tSQLt tests and the OpenAPI contract. The charts themselves belong to the frontend of Delivery Phase 2. Measured with 5,004 orders: the summary takes 4 ms, the best sellers 24 ms, the sales by category 178 ms and the weekly series of a whole year, the slowest, 227 ms, all below the 1 s of the design.
- **The background jobs exist** (D-06). A runner inside the API process runs the payment and reservation expiry every 60 seconds, the purge of idempotency keys and the reconciliation of amounts and inventory every day. Each job is a procedure that takes a session `sp_getapplock`, so several replicas are safe (the second one answers `Skipped`). 13 backend unit tests, 9 tSQLt tests and two concurrency scenarios. `GET /admin/system/jobs` and `/admin/system/reconciliation` show the state. D-08 is still open.
- **The customer and administration API exists** (blocks 7b and 7c). 66 operations under `/api/v1`: public catalogue, cart (visitor or customer), addresses, checkout (methods, reservation, order), the customer's orders and payments, deposit proofs (multipart, checked by their bytes, stored under an opaque key), and for staff the order status, returns, deposit review, bank accounts, refunds, inventory ledger, coupons, accounts, audit log and system versions. The OpenAPI contract describes all of them and a test keeps it equal to the routes. 216 backend unit tests (91 % of lines) and 14 HTTP flows against a real SQL Server, including the IDOR cases. 473 tSQLt tests; ten readers were added for the API. Missing: the dashboard endpoints and the job runner (block 8), and the generated client.
- **The backend has its security platform and authentication** (first part of Block 7). Argon2id passwords, JWT access tokens with rotating refresh tokens, authentication and role middleware, the idempotency middleware over `SP_Idempotency_*` and the layered rate limiter (D-05 is now closed on the code side), plus the five `/api/v1/auth` endpoints, verified against a real SQL Server (registration, login, renewal, reuse detection). 116 backend unit tests; 444 tSQLt tests. - **Order lifecycle, returns and refunds exist** (Block 6 of the plan to the delivery). `SP_Orders_ChangeStatus`, `SP_Orders_Cancel` (pending and paid orders), `SP_Returns_Register` with `FU_Orders_RefundableAmount` (the last unit closes the line to the cent), `SP_Refunds_Mark` and `SP_Refunds_List`, and `VW_Reconciliation_Amounts`, which returns zero rows after every scenario. 43 new tSQLt tests (442 in total). - **Deposit payments exist** (Block 5 of the plan to the delivery). `SP_Payments_ConfirmPayment` (idempotent, serialised by the payment lock, decrements the stock and writes the ledger), `RegisterProof`, `ApproveDeposit`, `RejectDeposit`, `CreateDepositAttempt`, `RegisterOrphanPayment`, `ExpirePending` and the internal `SP_Orders_CancelPending`. 45 new tSQLt tests (399 in total); procedure coverage is 56 of 56. Two races with real connections: twenty simultaneous confirmations decrement the stock once, and an operator approving while another rejects ends in one outcome. The second one found a deadlock that is fixed (see the catalogue). The expiry job is still pending (D-06).
- **Order creation exists** (Block 4 of the plan to the delivery). `SP_Orders_CreateOrder` builds the order, its lines, its payment and the links in one transaction from an active reservation, recalculating every amount in integer cents (the backend sends none). The design's numeric example now runs end to end: a 10 % coupon over Q245.45 gives Q24.54 split as 14.50, 4.50 and 5.54, total Q220.91, VAT Q23.67. It handles card and deposit (with the ADR-0016 window), stops an order whose coupon stopped being valid, and is idempotent by key. 35 new tSQLt tests (354 in total); procedure coverage is 48 of 48. Two races are proven with real connections: ten clicks on the same reservation create one order, and of twenty customers racing for the last use of a coupon exactly one gets it.
- **Idempotency exists** (Block 3 of the plan to the delivery). `SP_Idempotency_Begin`, `Complete`, `Fail` and `PurgeExpired` implement the first level of ADR-0004 in the database: one execution per key, replay of the stored response, `409` while in progress, `422` for another body, takeover after 60 seconds and a retry after a failure. 22 new tSQLt tests (319 in total) and a concurrency check with 100 simultaneous connections; procedure coverage is 47 of 47. The middleware that calls them is still pending (D-05).

Editing the cart releases its reservation. 63 new tSQLt tests (297 in total); procedure coverage is 43 of 43.
- **The stock ledger exists** (Block 1 of the plan to the delivery). `SP_Inventory_RegisterEntry`, `SP_Inventory_AdjustStock` and `SP_Inventory_GetLedger`, plus `VW_Inventory_Availability` and `VW_Inventory_Reconciliation`, which returns zero rows. Account lockout and refresh-token reuse detection live in the database. A mutation check confirmed that the anti-IDOR test of addresses fails when the ownership condition is removed.
- **A real race in the test SQL Server was fixed.** A fresh container with `MSSQL_COLLATION` accepts connections and then changes its default collation inside the process for about ten seconds; creating a database in that window made the server stop. The runner now reads the server log and waits until the change has finished (a first attempt that waited for `msdb` was not enough: the collation property already shows the new value when the change starts). Verified twice on fresh containers, launching the migration immediately.
- **The atomic stock reservation exists and its guarantee is proven under real concurrency.** `SP_Inventory_ReserveStock`, `SP_Inventory_ReleaseCartReservation` and `SP_Inventory_ReleaseExpiredReservations` (18 tSQLt tests, 101 in total) plus migration `V0011` (one active reservation per cart in the data). The new `npm run sql:concurrency` step of the `sql-tests` job fires up to 100 parallel connections: 100 buyers for 1 unit give exactly 1 success, 100 for 10 give exactly 10, and a cart with one unavailable line holds nothing. It found a real deadlock (60 carts with the same variants in different order lost 44 of them); the procedures now lock variants in ascending order and none are lost. The expiry job that calls `ReleaseExpiredReservations` is still pending (D-06).
- **Stage 3 has started with the money functions.** `FU_Money_HalfEvenDivision` and `FU_Money_VatIncluded` exist with the `Test_Money` tSQLt class (83 tests in total, all green locally on a fresh SQL Server). The TypeScript oracle `divRoundHalfEven` reads the same test vectors from the SQL test file, so the two implementations cannot drift apart silently.
- **The database collation is decided and enforced** ([ADR-0025](../adr/0025-database-collation.md)): `Latin1_General_100_CI_AS_SC`. The runner creates the database with it and stops with `COLLATION_MISMATCH` otherwise; every SQL Server the repository starts (compose, tSQLt server, CI) is initialised with the same collation, and a test fails if the places diverge. The tSQLt suite has 75 tests. A volume created before this change must be recreated with `docker compose down --volumes`.
