## Spike results

- **tSQLt works on the Linux SQL Server image and on Docker Desktop (WSL2)**, so the first risk of the register is closed and plan B is not needed. It was verified with tSQLt 1.0.8083.3529 on SQL Server 2022 CU27, starting from `clr strict security` enabled. A failing test makes `sqlcmd -b` exit with code 1 and the results export as JUnit XML. The lessons for writing the tests (identity values are not rolled back, test order is not fixed) are in [the tSQLt testing document](../quality/sql-testing-tsqlt.md#spike-result-29-october-2026).

- **Deposit payments exist** (Block 5 of the plan to the delivery). `SP_Payments_ConfirmPayment` (idempotent, serialised by the payment lock, decrements the stock and writes the ledger), `RegisterProof`, `ApproveDeposit`, `RejectDeposit`, `CreateDepositAttempt`, `RegisterOrphanPayment`, `ExpirePending` and the internal `SP_Orders_CancelPending`. 45 new tSQLt tests (399 in total); procedure coverage is 56 of 56. Two races with real connections: twenty simultaneous confirmations decrement the stock once, and an operator approving while another rejects ends in one outcome. The second one found a deadlock that is fixed (see the catalogue). The expiry job is still pending (D-06).
- **Order creation exists** (Block 4 of the plan to the delivery). `SP_Orders_CreateOrder` builds the order, its lines, its payment and the links in one transaction from an active reservation, recalculating every amount in integer cents (the backend sends none). The design's numeric example now runs end to end: a 10 % coupon over Q245.45 gives Q24.54 split as 14.50, 4.50 and 5.54, total Q220.91, VAT Q23.67. It handles card and deposit (with the ADR-0016 window), stops an order whose coupon stopped being valid, and is idempotent by key. 35 new tSQLt tests (354 in total); procedure coverage is 48 of 48. Two races are proven with real connections: ten clicks on the same reservation create one order, and of twenty customers racing for the last use of a coupon exactly one gets it.
- **Idempotency exists** (Block 3 of the plan to the delivery). `SP_Idempotency_Begin`, `Complete`, `Fail` and `PurgeExpired` implement the first level of ADR-0004 in the database: one execution per key, replay of the stored response, `409` while in progress, `422` for another body, takeover after 60 seconds and a retry after a failure. 22 new tSQLt tests (319 in total) and a concurrency check with 100 simultaneous connections; procedure coverage is 47 of 47. The middleware that calls them is still pending (D-05).
- **The cart and the coupons exist** (Block 2 of the plan to the delivery). Six cart procedures, five coupon procedures and six pure functions, including `FU_Cart_Totals`, which `CreateOrder` will reuse. There is no shipping: the brief does not ask for it. The design's numeric example is now a test (a Q24.54 discount split as 14.50, 4.50 and 5.54, total Q220.91, VAT Q23.67). A coupon that expires, sells out or is used after being applied stops discounting and the cart says why. Editing the cart releases its reservation. 63 new tSQLt tests (297 in total); procedure coverage is 43 of 43.
- **The stock ledger exists** (Block 1 of the plan to the delivery). `SP_Inventory_RegisterEntry`, `SP_Inventory_AdjustStock` and `SP_Inventory_GetLedger`, plus `VW_Inventory_Availability` and `VW_Inventory_Reconciliation`, which returns zero rows. Stock now enters only through the ledger, and the concurrency check races 50 simultaneous entries. 21 new tSQLt tests (234 in total); procedure coverage is 32 of 32.
- **Authentication and the catalogue exist.** 23 procedures (`SP_Audit_Record`, `SP_Users_*`, `SP_Tokens_*`, `SP_Categories_*`, `SP_Products_*`, `SP_Variants_*`, `SP_Addresses_*`) with 112 new tSQLt tests (213 in total); procedure coverage is 29 of 29. Account lockout and refresh-token reuse detection live in the database. A mutation check confirmed that the anti-IDOR test of addresses fails when the ownership condition is removed.
- **A real race in the test SQL Server was fixed.** A fresh container with `MSSQL_COLLATION` accepts connections and then changes its default collation inside the process for about ten seconds; creating a database in that window made the server stop. The runner now reads the server log and waits until the change has finished (a first attempt that waited for `msdb` was not enough: the collation property already shows the new value when the change starts). Verified twice on fresh containers, launching the migration immediately.
- **The atomic stock reservation exists and its guarantee is proven under real concurrency.** `SP_Inventory_ReserveStock`, `SP_Inventory_ReleaseCartReservation` and `SP_Inventory_ReleaseExpiredReservations` (18 tSQLt tests, 101 in total) plus migration `V0011` (one active reservation per cart in the data). The new `npm run sql:concurrency` step of the `sql-tests` job fires up to 100 parallel connections: 100 buyers for 1 unit give exactly 1 success, 100 for 10 give exactly 10, and a cart with one unavailable line holds nothing. It found a real deadlock (60 carts with the same variants in different order lost 44 of them); the procedures now lock variants in ascending order and none are lost. The expiry job that calls `ReleaseExpiredReservations` is still pending (D-06).
- **Stage 3 has started with the money functions.** `FU_Money_HalfEvenDivision` and `FU_Money_VatIncluded` exist with the `Test_Money` tSQLt class (83 tests in total, all green locally on a fresh SQL Server). The TypeScript oracle `divRoundHalfEven` reads the same test vectors from the SQL test file, so the two implementations cannot drift apart silently.
- **The database collation is decided and enforced** ([ADR-0025](../adr/0025-database-collation.md)): `Latin1_General_100_CI_AS_SC`. The runner creates the database with it and stops with `COLLATION_MISMATCH` otherwise; every SQL Server the repository starts (compose, tSQLt server, CI) is initialised with the same collation, and a test fails if the places diverge. The tSQLt suite has 75 tests. A volume created before this change must be recreated with `docker compose down --volumes`.
- **`/health/ready` now checks the schema version.** `SP_System_GetSchemaVersion` returns the last applied migration; the backend compares it with a version it declares in code and answers 503 with `schema: outdated` until the migrations run, then recovers on its own. Verified in the compose stack: ready with the schema current, 503 and an error log with the numbers when migration 10 was hidden, 200 again after restoring it, and `/health/live` unaffected. The tSQLt suite has 70 tests.
- **A technical audit closed Stage 2** ([QA-AUD-001](../quality/technical-audit-stage-2.md)): production vulnerabilities went from five to zero, seven foreign key indexes were added (`V0010`), certificate trust became configurable, shutdown is bounded, containers drop their capabilities, CI builds every image and checks the migration register against the files. Eight items remain registered as debt (the small ones D-09, D-10 and D-12 are closed); none blocks Delivery Phase 1.
- **The runner is the `db-migrate` service.** `db/runner/Dockerfile` builds it in two stages on `node:26-slim` with a non-root user. It was checked by building and starting the whole compose stack: the schema and seeds are applied, a second run changes nothing, the application login can run procedures but cannot read a table, and rotating `DB_APP_PASSWORD` realigns the login. The backend and frontend images had stopped building since the `db/tests/scripts` workspace was added (their `npm ci` did not find it); that is fixed.
- **`sql:coverage` is back in the job.** `sp-coverage.ts` fails when a critical procedure has no tSQLt test; today it reports 0 procedures and the 11 critical ones still to be built.
- **The reference seeds exist.** `S0001` to `S0005` load the roles, the order and payment states with their transitions, the payment methods, the inventory movement types and the ten configuration settings. A new `Test_Seeds` class checks each table against the documented values, and the suite now has 65 tests. Re-running a seed changes nothing and does not overwrite a tuned setting. The migration register marks V0001 to V0009 as applied after pull request #18 and lists the seeds. Demo data (catalogue, coupons, bank account, demo accounts) and the performance seed are still to come.
- **The core schema exists.** Migrations `V0001` to `V0009` create 40 tables (plus the two control tables of the runner) of the design with the glossary names, their `CHECK` constraints and filtered unique indexes, the insert-only and frozen-amount triggers, the transition triggers and the DDL capture. The tSQLt suite grew from 4 to 52 tests (schema shape, every constraint and trigger on the real tables) and passes in a throwaway SQL Server 2022, which also found a flaw in the design: a `UNIQUE` constraint on the nullable `GuestToken` would have allowed one signed-in cart in total. Reference rows (roles, statuses, transitions, payment methods) and the configuration values arrive with the seeds.
- **The migration runner works** (`npm run db:migrate` and `db:verify`, in `db/runner`). It was verified against SQL Server 2022 with fixture scripts: a first run, a repeated run that changes nothing, an edited migration (rejected), a changed object without a version bump (rejected), a raised version (applied, with its extended property), a hand-edited procedure (`db:verify` fails) and a broken migration (rolled back and logged). No real migrations exist yet: V0001 to V0009 come next.
- **`npm run sql:test` runs tSQLt end to end.** `db/tests/scripts/run-tsqlt.ts` keeps `ShopCart_CI` on a throwaway server (`npm run sql:test:up`), installs tSQLt on top of whatever schema is there, runs the tests in `db/tests/tsqlt` writes `test-results/tsqlt-junit.xml` and uninstalls tSQLt again. After a migration plus two runs the migrated table was still there and neither the tSQLt schema nor its CLR assembly remained. It was verified on SQL Server 2022 with a passing run, a repeated run and a forced failure (exit code 1). The first class, `Test_Environment`, checks the pinned version, the CLR permission set, TRUSTWORTHY and the `_CI` name.
- **tSQLt is vendored** in `db/tests/tsqlt/install` at version 1.0.8083.3529. The files keep their Windows line endings, so `.gitattributes` marks them `-text`, and `npm run sql:lint` verifies them against `SHA256SUMS`, also in the Windows job. A clone with `core.autocrlf=true` kept all three checksums.
